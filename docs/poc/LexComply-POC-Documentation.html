1. Executive Summary

LexComply Intelligence is a Legal & Compliance Research Assistant built as a microservices proof of concept. It manages policies, regulations, compliance assessments, reports and users, and layers a compliance intelligence platform on top: an Executive Command Center, an explainable Risk Scoring Engine, a Compliance Health Score, a Risk Heatmap, Gap Analysis, a Compliance Maturity Index, a Policy Approval Workflow, an Audit Timeline, an Executive PDF Report, Role-Based Dashboards, Global Search (⌘K), Dark Mode and an AI Compliance Copilot.

The platform is positioned in the same product category as Microsoft Purview Compliance Manager, ServiceNow GRC, RSA Archer and MetricStream, and the documentation below explains how each capability works, where it lives in the code, and how it can evolve into a full AI-driven GRC product.

Key outcomes

  • Five Spring Boot microservices behind a Spring Cloud Gateway, backed by PostgreSQL, documented with Swagger/OpenAPI.
  • A React enterprise shell (sidebar, top bar, command palette, Copilot drawer) with live data refreshed every 60 seconds.
  • A pure, unit-tested intelligence layer (risk, maturity, gaps, recommendations, workflow, copilot) with zero new npm dependencies.
  • Production build compiles with no ESLint warnings; 10 automated tests pass.

2. Objectives and Scope

2.1 Objectives

  1. Demonstrate an end-to-end microservices architecture (React → API Gateway → services → PostgreSQL).
  2. Transform a CRUD application into a decision-support product for executives, compliance officers, auditors and administrators.
  3. Make every score explainable (no “black box” numbers).
  4. Be AI-ready: define a contract for a future Retrieval-Augmented Generation (RAG) service.

2.2 In scope

  • Registers: Policies, Regulations, Compliance Assessments, Reports, Users.
  • Intelligence: health, risk, maturity, gaps, recommendations, heatmap, analytics, timeline, workflow, executive report, copilot.
  • UX: enterprise layout, responsive design, dark mode, global search, role-based dashboards, print-ready reports.

2.3 Out of scope (POC)

  • Authentication/authorization (JWT, Keycloak) – role switcher is a UI persona only.
  • Server-side persistence of workflow decisions and risk scores.
  • LLM / vector search integration (contract defined, not deployed).

4.2 Request flow

  1. PlatformDataProvider mounts and calls getPlatformSnapshot().
  2. The snapshot probes all five services in parallel (Promise.all) through the gateway and records status (UP/DOWN) and latency per service.
  3. Each request carries an X-Correlation-Id header (UUID) so a UI action can be traced in gateway and service logs.
  4. The raw datasets are passed to buildIntelligence() (pure function) which returns health, risk, maturity, gaps, heatmap, analytics and recommendations.
  5. All pages consume the same memoised intelligence object; data refreshes automatically every 60 seconds or on demand.
  6. If a service is down, the platform shows a “Degraded” indicator instead of failing completely.

7.3 Design principles

  • Separation of concerns: engines are framework-free pure functions; React only renders.
  • Single source of truth: one data snapshot, one intelligence object shared by every page.
  • Configuration-driven navigation: routes, sidebar and role access come from navigation.js.
  • Graceful degradation: per-service health probing; partial data still renders.
  • Design tokens: CSS variables drive light/dark themes and chart colours.
  • Accessibility: focus-visible outlines, ARIA labels, reduced-motion support, colour + text for status.

9. Intelligence Engines (Algorithms & Formulas)

9.1 Status classification

Status text is normalised to lower case and matched in order (non-compliant is tested before compliant):

Pattern (regex) Class Severity
(non|not)[ _-]?compliant | fail | violat | breach NON_COMPLIANT 1.0
partial PARTIAL 0.6
pending | progress | review | open | draft UNDER_REVIEW 0.4
compliant | pass | approved | closed | complete COMPLIANT 0.0
(anything else) UNKNOWN 0.5

9.2 Remark risk signals

Pattern Signal Weight
breach | leak | incident Incident indicator +12
penalt | fine | sanction | enforcement Regulatory penalty exposure +10
critical | urgent | severe Escalated severity +8
expired | overdue | outdated | lapsed Lapsed control +6
missing | absent | no evidence | not documented | gap Missing evidence +6

9.3 Multipliers

Factor Rule Multiplier
Jurisdiction EU / European Union ×1.20
Jurisdiction USA / US / United States / UK / United Kingdom ×1.10
Jurisdiction India ×1.05
Framework GDPR, HIPAA, SOX, PCI, DPDP, CCPA, Basel, DORA, NIS2, ISO 27001 in regulation name ×1.15

9.4 Residual risk score

if status = COMPLIANT:
    risk = 0
else:
    raw  = (severity × 70 + Σ signal weights) × jurisdiction × framework
    risk = clamp(round(raw), 1, 100)

Example: NON_COMPLIANT GDPR (EU) with remarks “Breach risk, penalty exposure” → (70 + 12 + 10) × 1.2 × 1.15 = 126.96 → 100 (Critical).

Every score returns a drivers list (e.g. “Status: Non-Compliant”, “Incident indicator in remarks (+12)”, “Jurisdiction weight EU (x1.2)”) – this is shown in the heatmap drill-down as “Why this score”.

9.5 Risk levels

Level Score Colour
Critical ≥ 85 Dark red
High 65 – 84 Red
Medium 40 – 64 Amber
Low < 40 Green

9.6 Compliance Health Score

Health = round(100 − mean(risk of all assessments))       (null when there are no assessments)
Bands:  ≥ 85 Strong   |   70–84 Watch   |   < 70 Critical

9.7 Coverage and rates

Policy coverage      = policies with ≥1 assessment / total policies
Regulation coverage  = regulations with ≥1 assessment / total regulations
Compliance rate      = COMPLIANT assessments / total assessments

9.8 Compliance Maturity Index

Dimension Definition Weight
Control Coverage average(policy coverage, regulation coverage) 30%
Control Effectiveness compliance rate 40%
Assessment Completeness 1 − (under review / assessments) 15%
Reporting Cadence min(1, reports / regulations) 15% 
Index = round(100 × Σ weight × value)
Level Name Index ≥ Meaning
1 Initial 0 Ad-hoc controls with limited visibility
2 Repeatable 20 Core controls exist but coverage is inconsistent
3 Defined 40 Standardised assessments across key regulations
4 Managed 60 Quantitatively measured and reported compliance
5 Optimizing 80 Continuous, data-driven improvement

The weakest dimension is reported as the focus area for reaching the next level.

9.9 Gap Analysis

  • Uncovered regulations – no assessment; exposure High if a high-impact framework, otherwise Medium.
  • Unassessed policies – policy never tested against any regulation.
  • Failing controls – assessments with risk ≥ 65 (High/Critical).
  • Data-integrity issues – assessments referencing a policy or regulation id that does not exist.

9.10 Recommendation engine

Source Priority Uplift
Each open finding (risk > 0) P1 if ≥ 65, P2 if ≥ 40, else P3 round(risk / number of assessments) health points
Uncovered regulation P1 (high-impact framework) / P2 –
Unassessed policy P3 –
Next maturity level P2 –

Sorted by priority, then by uplift (largest first).

9.11 Policy Approval Workflow (state machine)

From To Action Allowed roles Gate
DRAFT LEGAL_REVIEW Submit for Legal Review Compliance Officer, Admin –
LEGAL_REVIEW COMPLIANCE_REVIEW Legal Sign-off Compliance Officer, Admin –
COMPLIANCE_REVIEW EXECUTIVE_APPROVAL Compliance Sign-off Compliance Officer, Admin Blocked while any linked assessment has risk ≥ 65
EXECUTIVE_APPROVAL PUBLISHED Approve & Publish Executive, Admin –
LEGAL / COMPLIANCE REVIEW REJECTED Reject Compliance Officer, Admin –
EXECUTIVE_APPROVAL REJECTED Reject Executive, Admin –
REJECTED DRAFT Reopen as Draft Compliance Officer, Admin –

Initial stage is derived from evidence: no assessments → DRAFT; all compliant → PUBLISHED; otherwise → COMPLIANCE_REVIEW. Manual decisions (with actor, role and timestamp) are stored in localStorage key lca.workflow.v1 and appear in the approval trail and Audit Timeline.

9.12 Copilot engine (local intelligence mode)

Order of resolution: (1) entity match – a policy title or regulation name in the question; (2) intent match; (3) help response.

Intent Trigger words Answer
Summary summary, brief, executive, board, overview, posture Executive brief: health, maturity, risks, coverage, top 3 recommendations
Health health, score, how are we, compliant are Health score, method, compliant vs open findings
Maturity matur, cmmi, level Level, weakest dimension, all dimensions
Gaps gap, uncovered, missing, not covered, unassessed Uncovered regulations, unassessed policies, failing controls
Recommend recommend, what should, next step, fix, remediat, priorit, action Top 5 recommendations with uplift
Risk risk, critical, non-compliant, fail, violation, breach, exposure High/Critical findings with citations

Every answer contains: title, summary lines, clickable items (navigate to the relevant page), numbered citations, follow-up suggestions, and a grounded: true flag.

16. Interview Talking Points and Q&A

16.1 Talking points

  • Microservices + API Gateway: single entry point, CORS centralised, independent deployability per domain.
  • Explainable risk: deterministic, unit-tested scoring with drivers – auditors can reproduce any number.
  • Resilience: parallel probing with per-service status; degraded mode instead of blank screens.
  • Observability-ready: correlation id on every request.
  • Separation of concerns: pure engines vs. React rendering; easy to migrate engines server-side.
  • Governance by design: maker-checker workflow, role gating, risk control gate, approval trail.
  • AI readiness: grounded answers with citations today; documented RAG contract for tomorrow.
  • Zero added dependencies: custom SVG charts and icons keep the bundle lean and theme-aware.

16.2 Likely questions

Question Answer outline
Why compute risk on the client? The current data model has no risk field; computing client-side proved the model quickly. Engines are pure functions, so moving them to an intelligence-service is a lift-and-shift.
How do you prevent the Copilot from hallucinating? Local mode only uses platform data and always cites records. In RAG mode: permission-filtered retrieval, mandatory citations, refusal on low evidence, evaluation (faithfulness) in CI.
How is RBAC enforced? Today UI-only. Production: Keycloak OIDC, JWT validated at the gateway, role claims checked per route and in services; row-level security in PostgreSQL for tenancy.
What happens if a service is down? Promise.all over individually-caught probes; the service is marked DOWN, its data is empty, the UI shows “Degraded”, everything else works.
How would you scale this? Kubernetes + HPA, outbox/Kafka events, caching at the gateway, read models for analytics, OpenTelemetry tracing.
Why a maturity index? Executives need a trajectory, not just a snapshot; CMMI-style levels are familiar to boards and auditors.

2. RAG Knowledge Copilot

  • Value: cited answers across regulations, policies and evidence in seconds.
  • Architecture: ai-orchestrator-service implementing /assistant/ask; hybrid retrieval (vector + full-text, reciprocal rank fusion) with ACL filtering.
  • Backend: Spring AI ChatClient + QuestionAnswerAdvisor; Kafka-driven indexer (≈800-token chunks, 100 overlap); SSE streaming; PII redaction and prompt-injection guard.
  • Database: doc_chunks(…, embedding vector(1536), tsv tsvector, acl jsonb) with HNSW + GIN; ai_interactions.
  • Stack: Spring AI, pgvector, Azure OpenAI or Ollama (llama3.1, nomic-embed-text), RAGAS evaluation in CI.

3. Document Intelligence

  • Value: upload a regulation/policy PDF → extracted obligations, deadlines, penalties → suggested control mappings.
  • Backend: document-service; Tika/PDFBox/Tesseract or Azure Document Intelligence; Spring AI structured output (ObligationCandidate); confidence < 0.75 → review queue.
  • Frontend: upload wizard; split PDF/extraction review view.
  • Database: documents, obligation_candidates.

4. Regulatory Change Impact Analysis

  • Value: “Regulation amended → 7 policies, 12 controls, 3 owners affected → draft remediation plan.”
  • Backend: semantic clause diff (ADDED/REMOVED/MODIFIED); impact score = materiality × affected controls × current risk; RegulatoryChangeDetected event.
  • Frontend: Change Radar with clause diff and impact graph.
  • Database: regulation_versions, obligation_changes, impact_assessments.

5. Real-Time Event Backbone & Autonomous Monitoring

  • Value: continuous control monitoring instead of point-in-time audits.
  • Backend: Kafka topics (policy, compliance, regulation, control.signals, alerts); monitoring-service with declarative rules (e.g. evidence > 90 days, risk +20 in 24h); SSE push.
  • Database: monitoring_rules, alerts (with fingerprint de-duplication).
  • Stack: Kafka/Redpanda, Spring Cloud Stream, Debezium, Drools, Resilience4j.

6. Multi-Agent Agentic Workflows

  • Agents: Supervisor → Regulatory Analyst, Control Assessor, Policy Drafter, Audit Agent, Reporter.
  • Governance: tools = existing REST APIs (Spring AI @Tool / MCP); read tools autonomous, write tools require human approval; agent acts with the user’s identity; token budgets.
  • Frontend: Agent Console with live step trace and approval cards.
  • Database: agent_runs, agent_steps.

7. Compliance Knowledge Graph

  • Model: nodes Regulation, Obligation, Control, Policy, Evidence, Owner, Risk, System; edges REQUIRES, SATISFIED_BY, IMPLEMENTS, PROVES, OWNS, AFFECTS.
  • Uses: impact analysis, “test once comply many”, GraphRAG context expansion.
  • Stack: Apache AGE (inside PostgreSQL) or Neo4j; React Flow / Cytoscape.js.

8. Policy Recommendation & Drafting Engine

  • Gap → AI-drafted, cited clause → redline vs. current policy → existing approval workflow.
  • Database: policy_versions (author_type HUMAN/AI), clause_library (with embeddings).

9. Audit Intelligence

  • Hash-chained, append-only audit_log; segregation-of-duties anomaly detection; statistical sampling; one-click audit pack (PDF + ZIP with SHA-256 manifest).

10. Predictive Compliance & Risk Forecasting

  • Requires 8–12 weeks of risk_snapshots. Phase A: Holt-Winters forecasting; Phase B: gradient-boosted “control fails in 90 days” classifier with SHAP explanations.
  • Database: predictions, model_registry. Stack: Tribuo/Smile (Java) or FastAPI + LightGBM + MLflow.

11. Compliance Digital Twin & Executive Decision Support

  • Snapshot the model, apply scenario mutations (remediate controls, add regulation), re-run engines, compare before/after; optimiser suggests best remediation for a budget.
  • Database: scenarios, decisions. Stack: pure Java domain engine, Timefold (OptaPlanner).

Cloud-Native Enterprise Platform (cross-cutting)

  • Keycloak OIDC; JWT at gateway; OAuth2 client-credentials between services.
  • Multi-tenancy via tenant_id + PostgreSQL row-level security.
  • OpenTelemetry → Grafana / Tempo / Prometheus / Loki; LLM token, cost and quality metrics.
  • Docker Compose (dev), Kubernetes + Helm + Argo CD (prod), Vault for secrets, HPA on AI services.
  • CI: GitHub Actions, Testcontainers, RAG evaluation gate, OWASP dependency check, signed images + SBOM.
  • AI governance: prompt registry, model allow-list, PII redaction, EU AI Act use-case register.
